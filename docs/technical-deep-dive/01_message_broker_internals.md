# メッセージブローカーの内部動作

## 概要

メッセージブローカーは、Celeryの心臓部です。プロデューサー（タスクを送信する側）とコンシューマー（ワーカー）の間でメッセージを仲介します。

## Redisの内部構造

### データ構造

Redisは以下のデータ構造を使用してメッセージキューを実装します：

```

│  Type: LIST                                            │

│  │  Index 0: │ {"task":"add", "args":[1,2], ...}  │ │ ← RPUSH (追加)
│  │  Index 1: │ {"task":"mul", "args":[3,4], ...}  │ │
│  │  Index 2: │ {"task":"div", "args":[8,2], ...}  │ │
│  │     ...                                          │ │
```

### Redis Listの仕組み

```
List Operations (FIFO Queue):

Initial State:
HEAD ← [Task3] [Task2] [Task1] ← TAIL
        (oldest)      (newest)

RPUSH "Task4":  (Producer adds task)
HEAD ← [Task3] [Task2] [Task1] [Task4] ← TAIL

LPOP:  (Worker retrieves task)
Returns: Task3
HEAD ← [Task2] [Task1] [Task4] ← TAIL

BLPOP (Blocking POP):
- キューが空の場合、タスクが来るまでブロック
- タイムアウト指定可能
- 複数ワーカーが同時にBLPOPしても競合しない
  （Redisがアトミックに処理）
```

### Visibility Timeout (可視性タイムアウト)

```
Timeline:
T=0s   Worker1 receives Task A
       │
       ├─> ZADD unacked <current_timestamp> "task-A-id"
       │   (未ACKセットに追加、スコアはタイムスタンプ)
       │
       └─> Task A processing...

T=60s  Worker1 crashes (Task A incomplete)

T=120s Visibility timeout checker (別スレッド)
       │
       ├─> ZRANGEBYSCORE unacked 0 <now - visibility_timeout>
       │   (古い未ACKタスクを検索)
       │
       ├─> Finds "task-A-id"
       │
       └─> RPUSH celery {Task A message}
           ZREM unacked "task-A-id"
           (タスクを再度キューに戻す)

Normal completion:
T=5s   Task A completes
       │
       └─> ZREM unacked "task-A-id"
           (未ACKセットから削除)
```

## まとめ

### Redis
- **構造**: シンプルなLISTベース
- **速度**: 非常に高速
- **永続性**: 限定的（AOF使用でも最大1秒のデータロス）
- **適用**: 開発環境、高速性重視、短命なタスク

### RabbitMQ
- **構造**: Exchange-Queue-Bindingの複雑なルーティング
- **速度**: 高速（Redisより若干遅い）
- **永続性**: 優秀（クラッシュ耐性）
- **適用**: 本番環境、信頼性重視、複雑なルーティング

どちらを選ぶかは、要件次第です：
- **速度最優先** → Redis
- **信頼性最優先** → RabbitMQ
- **複雑なルーティング** → RabbitMQ
- **シンプルさ** → Redis
